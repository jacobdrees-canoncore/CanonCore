# Fast CI that never lies: audit and plan, without Blacksmith

**Short answer.** Two of the five repositories already meet the 2 min / 3 min target. The other three miss it because of test running time, not waiting or setup:

- **Extractor:** PR p50 257 s, p95 380 s. One pytest process runs 390 tests in 341 s on a 2-core runner.
- **The skills:** PR p50 120 s, p95 126 s. One Vitest run takes 106 s, and a single file takes 45 s of that.
- **untitled-app-replica:** PR p50 130 s, p95 538 s. A cold SwiftPM build plus a 32 s suite run on macOS, and macOS slots queue.

Waiting is under 10 s at p95 on every Linux job. Setup is under 30 s everywhere.

The brief's two outranking rules collide with the account's plans:

- **Merge queue.** GitHub offers it only on org-owned public repositories, or on private repositories under Enterprise Cloud. So only CanonCore can have one today.
- **Bigger runners.** GitHub's larger runners need Team or Enterprise Cloud. Every org here is on Free, and the skills repository is user-owned.

Two more findings change the order of work:

- **Extractor's org has nearly run out of Actions.** It had used $11.59 of its $12 monthly Actions allowance by 16 Nov.
- **The skills' `main` went red 11 times in two days.** That is what a merge queue exists to stop, and that repository cannot have one.

## Part 2: the audit

**Method.**

- The last 150 runs per repository were read with `gh run list -L 150` and every run's jobs with `GET /actions/runs/{id}/jobs`.
  - brink-replica has only 86 runs and untitled-app-replica 56, so all of theirs were used.
  - The windows: CanonCore 31 Oct to 16 Nov, skills 6 to 16 Nov, Extractor 15 to 16 Nov, brink 4 to 16 Nov, untitled 15 to 16 Nov.
- Each completed, non-skipped, non-cancelled job is split into four parts:
  - **waiting:** job created to started.
  - **setup:** started to the first real step. Setup steps are `Set up job`, checkout, `setup-*`, `npm ci`, the ffmpeg restore and the uv interpreter step.
  - **running:** the real steps.
  - **teardown:** post steps and `Complete job`.
- Jobs carried over from an earlier attempt (started before created) and Dependabot jobs are excluded.
- **PR end-to-end** is the first run's creation for a pushed head to the last job's completion. It covers every `pull_request` and `pull_request_target` run created within 60 s of the head's CI run. Drafts and cancelled runs are excluded.
- GitHub reports times to the second, so values of 3 s or less carry ±1 s.

**Other findings that bear on "never lies":**

- **The skills' `main` went red 11 times** between 10 Nov 12:20 and 11 Nov 17:19 UTC, every time in `npm test`. One run failed `dispatch/no-terminal-addressing.test.ts` with `EISDIR`. - **ADR 0016 conflicts with the brief.** It says CI runs `--affected` on PRs "with a nightly job running everything". The brief instead runs the full suite in a merge queue before `main`. That is an ADR change and needs `tracing-a-decision` before it lands.

## Part 3: the plan

General rules, applied below:

- **Waiting** already meets <10 s at p95 on every Linux job.
- **Setup** already meets <30 s everywhere, so the brief's setup items are hygiene, not the biggest bucket, in every repository.
- **Budgets in seconds** need a check step, because `timeout-minutes` is whole minutes at best. Each job ends with a step that fails when the job's real step ran past its budget. `timeout-minutes` stays as the hang backstop.
- **The pre-push hook** lives in a committed hooks directory, set up with `git config core.hooksPath` ([githooks](https://git-scm.com/docs/githooks), current). The hook runs format, lint and typecheck on the changed files.

Each PR's expected gain is an estimate from the audit above, not a measurement, until its own before/after runs exist.

### CanonCore (public; target already met: 21 / 41 s)

1. **`concurrency` with cancel-in-progress, and `timeout-minutes` on every job.**
   - Gain: no measured gain at p50. It stops a superseded run holding the queue. It meets the waiting rule by construction.
2. **`filter: blob:none` on the two full-history checkouts** (Secret scan, Standing decisions), and pin gitleaks to a digest.
   - Gain: setup p95 31 s and 15 s down towards the 2 to 4 s of shallow jobs. That should take about 10 to 20 s off PR p95 (estimate).
   - The pin is for honesty, not speed.
   - **Measured in CC-422 (16 Nov 2026), which overrides this item for Secret scan.** A temporary workflow ran each checkout five times each way, with the step that reads the history after it ([run 43900400462](https://github.com/jacobdrees-canoncore/CanonCore/actions/runs/43900400462)). Secret scan, checkout plus gitleaks, p50: **9 s full, 37 s blobless**. gitleaks scanned the same 91 commits and 1.40 MB either way, but fetched the blobs lazily. So Secret scan stays on full history. Standing decisions, checkout p50: **7 s full, 2 s blobless**, with its step 0 to 1 s either way. So it goes blobless.
3. **Merge queue on `main`.** Add `merge_group` to `on:` in `ci.yml` (and to Ticket links and Standing decisions where they are required checks), then add the "Require merge queue" rule to the existing ruleset.
   - This is the only repository where it is available on Free.
   - It interacts with `merge-if-green.sh`'s head pin (docs/research/automerge-head-pin.md, "The merge queue"). That note found it undocumented which head a merge group is built from, so measure it before relying on it.
4. **Record the toolchain choice before the monorepo exists (ADR change, traced).**
   - The brief's defaults (bun, oxlint, oxfmt, `bun check`) replace ADR 0016's pnpm.
   - Facts the trace needs:
     - Bun under Turborepo is stable, with open prune issues.
     - `bun check` exists and passes TS 7.0.2's conformance suite.
     - oxlint cannot be shown to cover every ESLint rule, and `all` excludes nursery and the plugins.
     - oxfmt is beta.
   - CanonCore is mostly Markdown today. Run oxfmt side by side with Prettier on `docs/` first, and list what differs (`printWidth` 100 vs 80 for one).
5. **When the first package lands:**
   - lint, typecheck, build and test as parallel jobs;
   - `turbo run … --affected` on PRs with `fetch-depth: 0` plus `filter: blob:none`;
   - the full `turbo run` in `merge_group`;
   - then the brief's deliberate hidden change, to confirm CI goes red.

   Budgets that do not apply yet: lint, typecheck, test shards, node_modules caching. There is no JavaScript yet.

#### The budgets CC-422 set

Each budget covers a job's real steps, from the clock step after checkout to `budget.py`. It was set from the real-step time of the 20 PR heads before CC-422 (to `38ac1f89`), with headroom for a whole-second clock and runner jitter:

| Job | Real steps before, p50 / max (s) | Budget (s) | Why this much |
|---|---|---|---|
| Secret scan | 4 / 17 | 30 | The step pulls the gitleaks image each run, and the pull is what varies |
| Standing decisions | 0 / 1 | 10 | A network fetch of the PR's head |
| Ticket links | 1 / 3 | 10 | A live read of the PR through the API |
| Agent docs, Claude hooks, Ticket links guard | 0 / 1 | 5 | Local checks only |

`timeout-minutes: 5` on every job stays the backstop for a hang.

### skills (private, user-owned; 120 / 126 s, running is the biggest bucket)

1. **Split `dispatch/dispatch-monitor.test.ts`** (45.4 s) into files of about 15 s or less.
   - Vitest shards by file, so no shard can finish faster than its longest file.
   - Gain: none alone, but it unblocks item 2.
2. **Shard the suite 3 ways** (`--shard=k/3`, blob reporter, `--merge-reports` job).
   - The 106 s of work would be about 35 to 45 s a shard, plus 10 s setup. Expected PR p50 is about 60 to 70 s (estimate).
   - Vitest shards by file count, not duration. Balance them by moving files, or by a small script that orders files by the durations Vitest reports. No built-in way exists.
   - Cost: 3 jobs at a 1-minute minimum each, against today's 2-minute job. About +50% Linux minutes, roughly $2 more a month.
   - "Buy cores before shards" is not possible here. Larger runners need Team or Enterprise Cloud, which a user-owned repository cannot have. The only core-buying route is a third-party runner (see the bills list).
3. **Try `isolate: false` and `sequence.shuffle`, side by side with today's run.**
   - The suite spawns real shell scripts, so isolation is probably a small share of its 106 s. Measure before keeping it.
   - Shuffle is for honesty. Turn it on only after a run with a fixed `sequence.seed` passes twice.
4. **Add oxlint (`-D all` plus the plugins it needs, nursery stated either way) and oxfmt.**
   - The repository has no linter or formatter today, so there is no ESLint or Prettier to delete. Both run in well under the 5 s budget by their own speed claims, but that is unmeasured here.
   - Typecheck already meets <5 s with TypeScript 7 (`tsc`, 0 to 1 s). `bun check` is an option, not a gain.
5. **bun for install and scripts, in place of npm.**
   - `npm ci` takes 2 s with a cache hit, so the measured gain is at most about 2 s.
   - Extractor's own `package.json` pins npm through `devEngines` for REA. That is a separate repository and is unaffected.
6. **Pre-push hook** running oxfmt, oxlint and `tsc` on changed files.
7. **Merge queue: not available.** It needs an org repository on Enterprise Cloud.
   - The 11 red pushes to `main` show the cost.
   - A no-cost guard closer to the rule: `merge-if-green.sh` refuses a head that is behind `main` (CI must have passed on a head that already contains `main`). The trade is rebase-and-rerun latency per merge.
   - Without rulesets this is convention, not enforcement. The repository answers 403 to rulesets until it is on Pro.
