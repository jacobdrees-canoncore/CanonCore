# Plex Web

This note records how Plex Web, Plex's browser client, is built and behaves: its screens and the server calls each makes, how it chooses between direct play, direct stream and a server transcode, what it decodes itself, and what it keeps in the browser. It was written for CC-289, a ticket of the Plex sweep (ADR 0024). It describes behaviour in CanonCore's own words (`GLOSSARY.md`); where Plex's own term is needed it is given once in code formatting. No Plex payload, file, code or screenshot is copied here, and every capture stayed outside the repository.

Each claim carries its evidence, and names the copy it came from: **bundled** (4.160.0, served by the server at `/web`) or **hosted** (4.162.1, app.plex.tv).

- **observed**: seen in Orca's browser or in a request made to this server on the date above, or read from the static JavaScript of the named copy.
- **documented**: stated by Plex, with the URL given.
- **disassembled**: not used. Plex Web is JavaScript, read statically; native analysis belongs to CC-292.

## Sources and method

- **Static.** The bundled copy was copied out of `Plex Media Server.app/Contents/Resources/Plug-ins-e5521bd8c/WebClient.bundle` (309 files, 22 MB; `Contents/VERSION` is the server's build, `current_sha.txt` names `webdesktopbundle@75ddd7b…`). REA's `analyze-javascript-application` read it as a directory: 208 JavaScript files parsed, 3,075 webpack modules (runtime `webpackChunkplex_web_client`), no parse failures, and no Electron main process, preload or IPC, as expected for a web app. REA's graph names few endpoints (Plex builds most URLs at run time), so the behaviour below was traced through the bundle with ripgrep, as the desktop note did. For the hosted copy, `app.plex.tv/desktop/` and the 26 script files the hosted session loaded were downloaded and searched the same way; its player chunks were not loaded and were not compared.
- **Live.** One tab in Orca's browser, opened with `orca tab create`, driven with `orca goto`, `snapshot`, `click`, `select`, `type`, `keypress`, `scroll` and `reload`, never `eval`. Not REA's browser and not Playwright. Two HAR files were recorded, one per copy (see the next section). The Orca browser already held a plex.tv session for the agents' account, which both copies used to sign in. The tab was closed afterwards.
- **Replayed decisions.** Because the HAR holds no response bodies, the transcode decisions were replayed with curl against `/video/:/transcode/universal/decision`, with the same parameters and profile augmentation the client sent and the client identifier changed.
- **Plex support articles**, fetched with curl because a direct fetch returns 403: [Plex Web App Settings](https://support.plex.tv/articles/200289408-plex-web-app-settings/) (modified 17 Dec 2024), [Streaming Media: Direct Play and Direct Stream](https://support.plex.tv/articles/200250387-streaming-media-direct-play-and-direct-stream/) (modified 27 Mar 2019) and [How to Use Secure Server Connections](https://support.plex.tv/articles/206225077-how-to-use-secure-server-connections/) (modified 24 Jul 2025). Plex's API reference, <https://developer.plex.tv/pms/>, is cited through the sibling note `server-api.md`.
- **The server** is the one CC-287 installed and claimed. CC-288 was using it at the same time, adding and removing its own libraries, so only the CC-287 stub Films were played on purpose (see "Kept out, and side effects").

### The HAR capture, and REA

- **What worked: `orca exec` passthrough.** `orca exec --command "network har start"` began recording on the active tab and `orca exec --command "network har stop <path>"` wrote a HAR 1.2 file whose creator is agent-browser 0.27.0 (observed). The bundled session gave 1,827 entries, the hosted session 377. Orca has no HAR command of its own, so `orca network` was needed only as a live view while driving the page.
- **What the HAR lacks.** No response bodies, and no WebSocket frames (observed). Request and response headers, query strings, status codes and timings are present.
- **What REA needed.** REA's `inspect-web-network-capture <path> har` rejected the raw file, because its HAR schema refuses `data:` and `blob:` URLs ("HAR schema validation failed: format" at the first `data:` entry). A copy with only the http(s) entries (1,778 and 372 entries; 20 `data:` and 29 `blob:` entries dropped from the bundled file, 5 `data:` from the hosted) was read in full. Every Plex token value found in either HAR, plus the token used for curl, was passed as `--sensitive-value` (four values with their URL-encoded forms): REA made 2,156 redactions in the bundled file, and a search of both REA outputs found none of the four values. REA blanks a whole URL when it holds a marked value, so the screen catalogue below was built from paths parsed out of the raw HAR, with the token stripped, and timed against a step log kept while driving.

## Playback

### How the client chooses

The choice is split between the browser and the server.

1. **The browser probes itself** (observed, static, both copies). At start-up Plex Web builds a capability table by asking the browser about specific formats. Direct play is granted for a type only if `HTMLMediaElement.canPlayType` answers `"probably"`; direct stream is granted if `MediaSource.isTypeSupported` accepts it. The probes are H.264 in MP4 (`avc1.42E01E`), HEVC in MP4 (`hvc1`, `hev1` and `hev1.2.6.L150.B0`, each at two resolution limits), VP8 and VP9 with Opus or Vorbis in WebM (granted as the `mkv` container with MIME type `video/webm`), and ALAC in MP4 for music. Plex documents the outcome: "For most browsers, this will mean MP4 files with H.264 video and AAC audio" (documented, [Plex Web App Settings](https://support.plex.tv/articles/200289408-plex-web-app-settings/)).
2. **The client asks for what it can do** (observed, bundled). Before playing, it calls `POST /playQueues?type=video&uri=server://{machineIdentifier}/com.plexapp.plugins.library/library/metadata/{id}&own=1&…`, fetches the Item again with `checkFiles=1&includeMarkers=1`, then calls `GET /video/:/transcode/universal/decision` with `path=/library/metadata/{id}`, `mediaIndex=0`, `partIndex=0`, `protocol=dash`, `fastSeek=1`, `hasMDE=1`, `location=lan`, `subtitles=burn`, `autoAdjustQuality=0`, `mediaBufferSize=102400`, `session`, and its own verdicts as `directPlay`, `directStream` and `directStreamAudio`. Its profile augmentation (`X-Plex-Client-Profile-Extra`) is small: `append-transcode-target-codec(type=videoProfile&context=streaming&videoCodec=h264,hevc&audioCodec=aac&protocol=dash)`, plus, when a quality cap applies, `add-limitation(scope=videoCodec&scopeName=*&type=upperBound&name=video.bitrate&value={kbps}&replace=true)` with `maxVideoBitrate={kbps}`. The rest of the profile is the server's built-in one for platform `Chrome` (see `server-api.md`).
3. **The server decides within that** (observed, replayed). It answers with decision codes and a per-stream `decision`.

What happened to each stub (observed, bundled; codes from the replayed decisions):

| File | Client sent | Server decided | What was fetched |
|---|---|---|---|
| Stub One: MP4, H.264 and AAC, 814 kbps | `directPlay=1` | `mdeDecisionCode` 1000, "Direct play OK." | The original file, `GET /library/parts/{id}/{changestamp}/file.mp4`, three 206 range requests, played in the browser's own video element. |
| Stub Two: MKV, H.264 and AC-3, 197 kbps | `directPlay=0&directStream=1&directStreamAudio=0` | 1001 "Direct play not available; Conversion OK." (direct play code 3000 "App cannot direct play this item. Direct play is disabled."). Video `copy`, audio `transcode` to AAC, in MP4 over DASH. | `GET …/start.mpd`, then `session/{id}/0/header`, `session/{id}/1/header` and numbered `.m4s` segments per stream. |
| Stub One with Home Streaming capped at 0.7 Mbps | `directPlay=0&directStream=0&maxVideoBitrate=720`, plus the `add-limitation` | 1001; video and audio both `transcode` | DASH, as above. |
| Stub Two with the same cap | the same as uncapped (`directStream=1`, no cap sent), since 197 kbps is under the cap | as uncapped | DASH, as above. |

**The client turned down a direct play the server would have allowed.** Replaying Stub Two's decision with `directPlay=1` returned "Direct play OK." with the MKV and AC-3 streams marked `direct` (observed, replayed). So for Plex Web the browser's own probe, not the server's profile, is what keeps an MKV or an AC-3 track off direct play. The 5 min 30 s CC-288 Film that was played by mistake (see below) also went out with `directPlay=0&directStream=1&directStreamAudio=1` over DASH (observed).

Plex documents the same three outcomes: direct play sends "the file … directly to the device without being changed"; direct stream is for streams that are compatible but in "an incompatible file container (.mkv, .avi, .wmv, etc.)", and may transcode the audio alone ("Partially-Transcoded Direct Stream"); otherwise the server transcodes (documented, [Direct Play and Direct Stream](https://support.plex.tv/articles/200250387-streaming-media-direct-play-and-direct-stream/)).

**Quality settings.** Home Streaming's "Use recommended settings" (on by default) plays "compatible content … at original quality and if content needs to be converted, it will be converted at maximum quality"; turning it off sets "a maximum quality that applies to both compatible and converted content" (documented, [Plex Web App Settings](https://support.plex.tv/articles/200289408-plex-web-app-settings/); observed: options from "Maximum" down to "0.7 Mbps"). "Play smaller videos at original quality" applies to Internet Streaming only (documented, observed). Settings, Plex Web, Debug has Direct Play and Direct Stream switches, both on by default (documented). These settings are saved to the account on plex.tv, not only in the browser (observed: `POST /api/v2/user/settings?sharedSettings=1` on every save, and the values come back in the user object as `localQuality`, `remoteQuality`, `useHomeStreamingRecommendedSettings`, `autoAdjustQuality`, `forceTranscodeProtocolHLS` and others).

### What it decodes itself

- **Nothing in software.** All decoding is the browser's. Direct play hands the file URL to the video element; everything else goes through Media Source Extensions (observed, static and live). Plex Web carries no software video or audio decoder (no WebAssembly decoder found; observed, static).
- **DASH through Shaka Player v3.3.1** (observed, static: the string "shaka-player" with player version "v3.3.1" in the ad integration of chunk 5540; the chunk also holds Shaka's `shaka.offline.Storage` and its `shaka_offline_db` IndexedDB store). Both server-converted sessions in this capture were DASH (`start.mpd`, fragmented MP4 `.m4s` segments, one adaptation set per stream). **hls.js** is bundled too (chunk 9473; the version literal there is 1.1.3), and a user setting `forceTranscodeProtocolHLS` switches the transcode protocol from DASH to HLS (observed, static). Which of the two plays Live TV was not traced.
- **Encrypted media**: the main file, Shaka's chunk and hls.js's chunk call `requestMediaKeySystemAccess` (observed, static). What uses it (presumably Plex's own online content, since a server file is not encrypted) was not exercised.
- **Segments carry no token.** The `.m4s` segments and `header` requests under `…/session/{id}/…` went out with no token at all (28 segments and 8 headers, all 200; observed). `start.mpd` and the decision carried it. This matches what CC-287 found for HLS.

### Timeline reports

(observed, bundled) Plex Web reports with `GET /:/timeline` (a GET with query parameters, not the POST the reference shows) carrying `ratingKey`, `key`, `state` (`playing`, then `stopped`), `time`, `duration`, `playbackTime`, `playQueueItemID` and `hasMDE`; from a library page it adds `context=source:content.library`, `row` and `col`. The first report came about 1 s after playback started; on the 5 min 30 s Film the next came 9 s later and a `stopped` report at close. `time` and `duration` are milliseconds, with `time` rounded down to a whole second (0, 9000, 14000) while `playbackTime` is the exact wall time played. **No report names a Version, Media or Part**: the Version is chosen in the decision (`mediaIndex`, `partIndex`), and progress is reported against the Item. After a stub ended the client called `/library/metadata/{id}/userState` on the server and on discover.provider.plex.tv; both returned 404. On the 14 s viewing no `viewOffset` was stored on the Item (checked afterwards). Plex's reference asks for a report about every 10 s on a LAN (documented, see `server-api.md`).

## Caching, connection loss and refresh

- **No local copy of the Library** (observed, static, both copies): no service worker registration, no Cache Storage, no Web SQL, and no IndexedDB use outside Shaka Player's offline module. The bundle ships `mockServiceWorker.js` (Mock Service Worker 0.49.1, a development tool) at the web root, but nothing registers it.
- **What the browser holds** (observed, bundled; key names only). `localStorage`: `myPlexAccessToken` (the token, 20 characters), `clientID`, `anonymousClientID`, `users` (the signed-in user: subscription, roles, features and `experienceSettings`, which mirror the account's settings, such as qualities, subtitle look, list styles and `lastSourcePivots`), `deviceSettings` (holding only `restorePlayQueue`), `sessionstats` and Statsig's feature-flag store. `sessionStorage`: `splashScreenViewed`. No Plex cookie on the server's origin. The hosted copy held the same keys apart from `deviceSettings`. No Item, Show or list of Items is stored.
- **Fetch per screen, every visit** (observed, bundled). Going from the library grid to an Item and back re-requested `/library/sections/2/all` and `/firstCharacter`; revisiting an Item re-requested its detail, `/related` and the online lookups; returning Home re-requested every online shelf. The server's API responses carry `Cache-Control: no-cache` (311 responses), so the HTTP cache does not serve them either; only images from `/photo/:/transcode` are cacheable (`max-age=259200`, 218 responses). A reload re-ran the whole start-up sequence above.
- **Losing the connection** (observed, bundled, using Orca's per-tab offline switch). With the network cut, the open library grid was replaced within seconds by a full-window message, "Plex is not reachable. We are unable to connect to plex.tv at this time." Nothing already fetched stayed browsable. The client kept probing `clients.plex.tv/monitoring/health` (at 2, 4, 6, 8, 10 and 12 s) and the server's `/media/providers`. When the connection came back it recovered on its own, re-ran start-up, and the library route showed "Not found" until it was opened again.
- **Live updates** (observed, static, both copies). The client opens the server's WebSocket `/:/websockets/notifications` with the token in the URL (`appendToken`) and handles `timeline`, `activity`, `playing`, `status`, `progress`, `transcodeSession.start`/`update`/`end`, `preference`, `update.statechange`, `reachability` and `backgroundProcessingQueue` messages. A second connection with `filters=log` feeds the server log console. agent-browser's HAR does not record WebSockets, so whether a `timeline` message makes an open screen re-fetch was not observed.

**Verdict on ADR 0014, "Fetching per screen, as Plex and Jellyfin do": confirmed for Plex Web.** Every screen asks the server (and plex.tv's online sources) for its own data each time it opens, lists are paged 50 at a time with `X-Plex-Container-*`, the HTTP cache is told not to keep them, and nothing of the Library is stored in the browser; without a connection the client shows nothing at all. This closes what `server-api.md` left open (its API allows a changed-since copy; Plex's own web client does not use it), and agrees with the desktop note.

## Tokens

(observed) The bundled copy sends `X-Plex-Token` **in the query string on every authenticated server request** (477 requests to `127.0.0.1:32400` and 46 to `plex.direct`), and never as a header there. Most plex.tv calls carry it in the query too (356 to clients.plex.tv); a few plex.tv services get it as a header. It also appends the token to image URLs passed through `/photo/:/transcode`, and to the WebSocket URL. The hosted copy did the same in its 377 requests. Plex Web's own token came from the PIN sign-in and differs from the one used for curl here.

**Verdict on ADR 0012, "Plex documents passing `?X-Plex-Token=`": confirmed, and Plex's own web client does it on every request.** The documentation side is settled in `server-api.md`. The web side adds that Plex Web puts the token in the URL even for ordinary API calls, where the Qt desktop build uses a header (`desktop-and-htpc.md`), while transcoded segments carry no token at all.

## Verdicts

- **ADR 0010, "Server transcoding as the fallback every client leans on, as Plex, Jellyfin and Emby's web and many TV clients do": confirmed for Plex Web.** Plex Web decodes only what the browser can, which its own probe narrows to MP4 or WebM with H.264, HEVC (where the browser has it), VP8 or VP9 and AAC, Opus or Vorbis. Anything else goes to the server: a container change (direct stream), an audio conversion (AC-3 was converted to AAC although the server would have allowed direct play), or a full transcode when a quality cap is set. Every conversion is the server's, delivered as DASH. Plex Web has no on-device decoder of its own.
- **ADR 0014, "Fetching per screen, as Plex and Jellyfin do": confirmed for Plex Web** (see Caching).
- **ADR 0012, "Plex documents passing `?X-Plex-Token=`": confirmed** (see Tokens).
- **ADR 0013, "Plex shares one offset in milliseconds (`viewOffset`) across the versions of an item": consistent on the web side, sharing not proven here.** Plex Web reports `time` in milliseconds against the Item (`ratingKey`) with no Version identifier, so the client gives the server nothing to keep per Version. Whether the server stores one offset across Versions is CC-288's.
- **ADR 0013, "Players report about every 10 seconds"** (CanonCore's own choice, which follows Plex): **consistent.** Plex Web reported about 1 s after start, then 9 s later, then on stop.
- **ADR 0011, "Plex and Swiftfin show their own picker"**: **unsettled here; the sentence is about Apple TV.** Plex Web does show its own picker: after a reload, once the account had a Plex Home (CC-288 had added a managed user), it opened "Select User" listing the Admin, the managed user and "Add User…", and switched with `POST /api/v2/home/users/{uuid}/switch` (observed). Plex documents a web setting, "Automatically sign in", that skips it by reusing "the last used Plex Home member" (documented, [Plex Web App Settings](https://support.plex.tv/articles/200289408-plex-web-app-settings/)). What Plex's tvOS app does is the iOS and tvOS ticket's.
