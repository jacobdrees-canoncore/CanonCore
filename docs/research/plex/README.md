# Plex research: index, verdicts and ADR clashes

This folder is the Plex sweep (ADR 0024, CC-285): Plex studied once across its whole surface, in public notes, so that CanonCore's ADRs and specs can cite what Plex does rather than what its support pages summarise. This README indexes the notes, gives a verdict on every Plex claim the 11 Oct 2026 trace listed (the CC-285 comment "The Plex claims this sweep must give verdicts on"), and lists every ADR sentence the notes contradict, for the Owner to decide one by one. No ADR is changed here.

Behaviour is described in CanonCore's words (`GLOSSARY.md`). Each verdict inherits its evidence class from the note it cites:

- **observed**: seen on the running server or in a client's traffic, or read from a shipped bundle with a standard tool.
- **disassembled**: from REA's Ghidra analysis of a Plex executable.
- **documented**: stated by Plex on its own pages, with the URL. Pages this note read itself carry the date read (18 Oct 2026) and the page's own modified date.

A verdict is **confirmed**, **contradicted** or **unsettled**. "Contradicted" is used only where a note's evidence refutes the sentence as worded; where only part of a sentence fails, the verdict says which part.

## Where the notes disagree

Later notes settle questions earlier ones left open, and in a few places they disagree. The verdicts below take the more direct evidence:

- **ADR 0010, server transcoding as the fallback.** [`server-behaviour.md`](server-behaviour.md#11-transcoding), [`server-inside.md`](server-inside.md#verdicts) and [`web.md`](web.md#verdicts) say confirmed; [`desktop-and-htpc.md`](desktop-and-htpc.md#verdicts-on-the-playback-claims) and [`ios-and-tvos.md`](ios-and-tvos.md#verdicts-on-the-playback-claims) say contradicted for their clients. They describe different clients. See A11 and the last part of "ADR sentences the notes contradict".
- **ADR 0014, fetching per screen.** [`server-api.md`](server-api.md#verdicts) and [`server-behaviour.md`](server-behaviour.md#verdicts) left it unsettled because they watched no client; the three client notes confirm it.
- **CC-2 story 33, "S2 · E3".** [`server-behaviour.md`](server-behaviour.md#verdicts) left it unsettled; [`web.md`](web.md#verdicts) observed it.
- **ADR 0011, Plex's own picker.** [`server-behaviour.md`](server-behaviour.md#verdicts) confirmed it from documentation only, [`web.md`](web.md#verdicts) left the Apple TV half open, and [`ios-and-tvos.md`](ios-and-tvos.md#7-verdicts) settled it from the Apple TV build.
- **Playlists after a move.** [`server-behaviour.md`](server-behaviour.md#2-file-identity-rename-move-missing) says a playlist holding the old Item is lost when a move makes a new Item; [`server-inside.md`](server-inside.md#4-the-other-open-questions) corrects this from the log and the program: the server re-points playlists. Collections were not seen re-pointed.
- **ADR 0004, keeping only the winner.** [`server-behaviour.md`](server-behaviour.md#8-metadata-agents) confirmed it as far as the API shows; [`server-inside.md`](server-inside.md#4-the-other-open-questions) settled it inside the program.
- **The timeline call.** Plex's reference and [`server-api.md`](server-api.md#endpoints) show a `POST /:/timeline`; [`web.md`](web.md#timeline-reports) observed Plex Web sending it as a GET. Both work; no verdict rests on the method.
- **Continue Watching's next Episode.** [`web.md`](web.md#verdicts) left it unsettled; [`server-behaviour.md`](server-behaviour.md#12-collections-smart-collections-playlists-continue-watching) observed it on the server.

## ADR sentences the notes contradict

*Plex sweep (ADR 0024), CC-293, 18 Oct 2026. From the notes in `docs/research/plex/`: Plex Media Server 1.43.4.10903, Plex Web 4.160.0 and 4.162.1, Plex desktop 1.115.0, Plex HTPC 1.71.1, Plex for iOS 2026.19.1 and Plex for Apple TV 2026.20.0. Each sentence is quoted as it stands on `main` today, for the Owner to decide one by one. No ADR has been changed.*

**1. ADR 0002 (`docs/adr/0002-no-default-provider.md`), the decision paragraph.**

> "…matching Plex and Jellyfin for video, where a local NFO overrides online data."

Contradicted for Plex. Plex's default video agents ignored a Kodi-format `.nfo` and `movie.nfo` beside a film, with "Prefer local metadata" off and on (observed, `server-behaviour.md`, section 8). Plex documents NFO support only as a separate agent, "Plex NFO Movie" or "Plex NFO Series", chosen per library and needing Server 1.43.1 or newer (documented, [Using NFO metadata files with Plex](https://support.plex.tv/articles/using-nfo-metadata-files-with-plex/)). The 1.43.4 server did not offer it: the program registers both NFO agents only when a runtime flag is set, most likely a remote feature flag (disassembled, `server-inside.md`, section 4). Even embedded tags win only with "Prefer local metadata" on, and it is off by default (observed).

**2. ADR 0002, the decision paragraph.**

> "Plex's music library is the exception: there its online agent wins unless "Prefer local metadata" is switched on (support.plex.tv, verified 2026-09-29)."

Contradicted as an exception; the music half holds. In a music library the online values won until "Prefer local metadata" was on (observed). Video libraries behave the same way: an MP4's embedded title and genre were ignored with the setting off and won with it on (observed). With the setting on, music genre and album art still follow their own per-library settings ("Genres", "Album Art") (observed, `server-behaviour.md`, section 8).

**3. ADR 0004 (`docs/adr/0004-sourced-statements-and-locks.md`), the decision paragraph.**

> "Plex's current agents have no source ordering, only a per-field "Ratings Source", and its legacy ordered agents are hidden for new libraries since Server 1.43.0"

Contradicted in two of its three parts.

- Source ordering exists. Since Server 1.43.0 a library is bound to a Metadata Agent, an ordered group of providers (Plex Movie or Series, Plex Local Media and Custom Metadata Providers). The first provider with a value wins every field and later providers fill only the fields left empty; reordering the group and refreshing changed the winner (observed, `server-behaviour.md`, sections 7 and 8; documented in Plex's API reference, "Metadata Providers").
- "Ratings Source" is one setting per movie library, with three values, not a per-field choice (observed; documented: "Select the rating source for this library", [Plex Movie agent advanced settings](https://support.plex.tv/articles/advanced-settings-plex-movie-agent/)).
- The legacy part holds: legacy agents are hidden during library setup unless "Show legacy agents during library setup" is on, since 1.43.0 (documented in Plex's 1.43.0 release notes; observed).

The same claim sits in CC-10's comment 76150a54, and the prototype snapshot's "the ecosystem's one list per library (ADR 0004)" already matches what Plex does.

**4. ADR 0015 (`docs/adr/0015-missing-file-goes-offline.md`), the decision paragraph.**

> "The fingerprint is CanonCore's own design, as neither Plex nor Emby documents its file hash."

Contradicted as worded; it holds for the algorithm. Plex documents that each file row carries two hashes: its API reference shows `hash` and `openSubtitleHash` on the file in its `/library/metadata/{id}/tree` example, and describes `computeHashes` as computing "Plex and OpenSubtitle hashes" (documented, `server-api.md`, Verdicts). It documents neither algorithm. The program shows the Plex hash is the SHA-1 of the decimal file size followed by the hex SHA-1s of the file's first and last 64 KiB, with a shortcut for files under 64 KiB, and the other is the public OpenSubtitles hash (disassembled, and observed by recomputing both on five files, `server-inside.md`, section 1). Two points for ADR 0015's reasoning: Plex reuses a renamed or moved file's Version only when the old file is gone and the title, year and Edition parsed from the new path still agree; and two files that share their size, first 64 KiB and last 64 KiB get the same Plex hash (disassembled, observed, `server-inside.md`, section 2). The CC-2 scanner sentence repeats the claim.

**Considered and not listed: ADR 0010 (`docs/adr/0010-codecs-on-device-transcode-optional.md`), Considered Options.**

> "Server transcoding as the fallback every client leans on, as Plex, Jellyfin and Emby's web and many TV clients do: rejected as the only path, because it fails on a host that forbids it. Their own first-party apps also decode on the device (Swiftfin with VLCKit, Plex HTPC with mpv), which is the half this record keeps."

Not contradicted as worded. The sentence names Plex's web and TV clients, and the same line already grants that first-party apps decode on the device, so `desktop-and-htpc.md`'s "contradicted" for Plex desktop is outside its scope.

- **Web: confirmed.** Plex Web lets the browser decode only what its probe accepts (MP4 or WebM with H.264, HEVC where the browser has it, VP8 or VP9, and AAC, Opus or Vorbis) and sends everything else to the server. It even had AC-3 converted to AAC when the server would have allowed direct play (observed, `web.md`, Playback).
- **TV clients: contradicted for the two studied, unsettled for "many".** Plex for Apple TV decides direct play on the device, declares every video codec playable, and decodes with FFmpeg by default; it transcodes only after a direct play error, a quality cap or for Live TV (observed and disassembled, `ios-and-tvos.md`, section 5). Plex HTPC, Plex's app for the TV screen, declares near-universal direct play and decodes in mpv (observed, `desktop-and-htpc.md`). Plex's Roku, Android TV, smart TV and console apps were not studied, so "many TV clients" is neither confirmed nor refuted.

One wording point for the Owner: every Plex client is first-party, so for Plex the sentence's split between "web and many TV clients" and "their own first-party apps" does not separate anything. On the evidence, Plex Web leans on the server and Plex's Apple TV, iOS, HTPC and desktop apps decode on the device.
