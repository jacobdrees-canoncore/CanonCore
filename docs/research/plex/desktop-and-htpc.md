# Plex desktop and Plex HTPC

11 Oct 2026. Plex desktop for macOS **1.115.0** (Info.plist `CFBundleShortVersionString` and `CFBundleVersion` both 1.115.0; build 1.115.0.426-4e960a1d, released 13 Aug 2026) and Plex HTPC for macOS **1.71.1** (both keys 1.71.1; build 1.71.1.346-f62ce923, released 30 Jul 2025, still the current macOS build on 11 Oct 2026). REA **6.4.0** (`npx -y rea-agents@latest --version`), with Ghidra 12.1.4 (Homebrew) and OpenJDK 21 as its native provider. Also used: `curl`, `shasum`, `ditto`, `plutil`, `lipo`, `otool -L`, `nm -u`, `strings`, `codesign` (through REA's `inspect-signature`) and `rg`. No browser was opened, no Plex account was used and neither app was launched (ticket CC-290, ADR 0024).

Each claim is marked **observed** (seen in the bundle with a standard tool or REA's inventory), **disassembled** (from REA's Ghidra analysis of the arm64 slice of the app's main executable) or **documented** (Plex's own pages or forum, with the URL). Behaviour is described in CanonCore's words (`GLOSSARY.md`). Where Plex's own term is needed it is given once in code formatting.

## Where the builds came from

- **observed**: `https://plex.tv/api/downloads/6.json` lists Plex desktop and `https://plex.tv/api/downloads/7.json` lists Plex HTPC (`5.json` is Plex Media Server). Both macOS entries point at `downloads.plex.tv` universal zips: `plex-desktop/1.115.0.426-4e960a1d/macos/Plex-1.115.0.426-4e960a1d-universal.zip` and `htpc/1.71.1.346-f62ce923/macos/PlexHTPC-1.71.1.346-f62ce923-universal.zip`. The SHA-1 of each download matched the checksum in the JSON (`2936058…` and `f179660…`).
- **observed** (REA `inspect-signature`): both are Developer ID signed by Plex Inc. (team K4QJ56KR4A), with hardened runtime. The only entitlements are `allow-unsigned-executable-memory` and `disable-library-validation`. There is no App Sandbox, so no network, file-access or local-network entitlements are declared, and none are needed outside the sandbox. Bundle IDs: `tv.plex.desktop` and `tv.plex.htpc`. Both are universal (x86_64 and arm64).

## What each is built with

Both apps are the same native shell. The differences are the web UI it loads and the input handling HTPC adds.

| | Plex desktop 1.115.0 | Plex HTPC 1.71.1 |
|---|---|---|
| Qt | 6.2.4 (QtCore Info.plist `CFBundleVersion`; `strings` gives "Qt 6.2.4 … by Clang 12.0.5") | 6.2.4, same evidence |
| Web engine | QtWebEngine 6.2.4, user agent token `Chrome/90.0.4430.228` (`strings` on QtWebEngineCore) | the same |
| Player | libmpv.2, `mpv 0.38.0` (`strings` on `Frameworks/libmpv.2.dylib`) | libmpv.2, `mpv 0.38.0` (a different binary, so a different build) |
| ffmpeg | Plex's own build: libavcodec 59.25.100, identified as "FFmpeg version 46f74ab-…" | the same version string |
| Web UI | Plex Web 4.160.0 (`webpackChunkplex_web_client`, files `*-plex-4.160.0-75ddd7b.*`, `current_sha.txt` `qtdesktop@75ddd7b…`), React | the TV client `tv-htpc@plex` 5.92.0-103e5b2 (`webpackChunk_plex_client_qt`), drawn with Lightning JS core 2.6.0 (`vendors-…lightningjs_core_2_6_0…`) |
| Extra native pieces | none | libcec 4 (HDMI-CEC), input maps for Apple Remote, CEC, DualShock 4, Xbox One and Series pads, keyboard |
| Embedded server | `PlexMediaServer.framework` (`tv.plex.nanoserver`), Plex Media Server 1.41.8.9834-071366d65, plus `MacOS/Plex Transcoder` | the same server version (a different binary), plus `Plex Transcoder` |

- **observed** (`otool -L` on each main executable): each links all of the Qt frameworks above, `libmpv.2.dylib`, the ffmpeg libraries, OpenSSL 3, and the `PlexMediaServer` framework in-process. HTPC also links libcec, ForceFeedback, CoreAudio and AudioToolbox.
- **observed** (`otool -L` on the ffmpeg and transcoder dylibs): libavcodec, libavutil and libavformat link VideoToolbox, CoreMedia and CoreVideo, and libavcodec contains `h264_videotoolbox` and `hevc_videotoolbox`. libmpv's build feature list includes `videotoolbox-gl`, `libplacebo`, `libass`, `luajit` and `coreaudio`. `Plex Transcoder` links VideoToolbox, Metal and OpenCL. The `strings` output of libavcodec also names Plex-specific decoders (`eac3_eae`, `truehd_eae`) and `libdav1d`.
- **observed** (REA `analyze-javascript-application` on each `Resources/web-client`): REA parsed 202 desktop files (3,092 modules) and 192 HTPC files (1,578 modules). It found no Electron main process, preload or IPC, as expected for a Qt app. Its graph lists HTPC's plex.tv routes and its local-storage use. In both UIs the bridge to the native side is Qt WebChannel (`QWebChannel` over `qt.webChannelTransport`), with the same deferred-return pattern on a `system` object (`rg` through the bundles). The desktop UI asks the native side for the product, version and platform (`system.describe`) and then sends them as headers.
- **disassembled** (REA `search --kind procedures` with Ghidra on both arm64 slices; symbols are present): the two executables share the same native classes, `MPVEngine`, `MPVPlayer`, `MPVRenderer`, `MPVOpenGLView`, `Player` and `NanoServerManager`/`NanoServer`, with the same method lists. HTPC adds `CECInput`, `CECInputWorker`, `InputManager` and `InputMapping`. mpv is driven through libmpv's render API (`nm -u`: `mpv_render_context_create`, `mpv_render_context_render`, `mpv_set_option_string`, `mpv_hook_add` and others), drawing into a Qt OpenGL view.
- **Verdict on the packager's claim** that both use Qt 6 and mpv ([negativo17](https://negativo17.org/plex-desktop-and-htpc-client/)): **confirmed** for macOS. Both are Qt 6.2.4 with QtWebEngine and libmpv (mpv 0.38.0).
- **Verdict on "HTPC plays through mpv"**: **confirmed**. It is observed above and **documented**: a forum guide says "Plex HTPC as well as Plex for Windows/Mac/Linux uses mpv as a playback engine" ([HTPC Tips and Tricks](https://forums.plex.tv/t/htpc-tips-and-tricks/794228), 25 May 2022, by a Plex Pass user not marked as staff), and Plex's HTPC release notes bump mpv ([release thread](https://forums.plex.tv/t/plex-htpc/703783), post 3, 20 Apr 2021).
- Both bundles ship `mpv.conf.sample`, `input.conf.sample` and a `scripts` folder. **observed**: the user can configure mpv in both apps, not only in HTPC.

## Playback: what each decodes itself

### HTPC

- **observed** (`getAppConfig_ts-…js` in the HTPC web client): the playback profile sends the server profile name `Generic`, with a cap of 4096 by 2160. Direct play is tried over DASH, then HLS, then plain HTTP. Transcoding uses plain HTTP. The video codecs declared for direct play are h264, hevc, mjpeg, vc1, mpeg2video, mpeg1video, mpeg4, msmpeg4v2/v3, wmv3, vp8, vp9 and av1, with direct streaming allowed for any other codec. The audio codecs are aac (including HE-AAC and LATM), alac, ac3, dca, eac3, flac, mp2, mp3, ogg, opus, pcm, truehd, vorbis and the wma family. Subtitles declared over HTTP are srt, ass, pgs and vobsub. One setting asks the server to keep Matroska attachments. These declarations travel as `X-Plex-Client-Profile-Extra` (`add-direct-play-profile`, `add-limitation`, `add-transcode-target-codec` and others) with `X-Plex-Client-Profile-Name`.
- **observed**: the server profile `Generic` in the bundled server's `Resources/Profiles` is empty, so HTPC's whole capability statement is the extra profile it sends. A `Konvergo` profile (Plex Media Player's old name) is also present: it transcodes to H.264 and Opus in MKV.
- **observed**: the HTPC UI has user settings "Allow Direct Play", "Allow Direct Stream" and "Force Direct Play", and the messages "Playback speed is only available while direct playing" and "Try turning off Force Direct Play and try again". **documented**: "Added a setting to force on direct play" (HTPC 1.57.1, [release thread](https://forums.plex.tv/t/plex-htpc/703783), post 61, 6 Mar 2024).
- **disassembled** (REA `function` on `MPVEngine::updateHardwareDecodingSetting`, HTPC and desktop): a single on/off hardware-decoding setting from the UI sets mpv's `hwdec` to `auto` or `no`. `MPVEngine::doSet` also refers to `auto-safe`. With libavcodec's VideoToolbox decoders, this means hardware decoding goes through VideoToolbox where mpv can use it, with software ffmpeg decoding otherwise.

### Desktop

- **observed** (`main-8792-…-plex-4.160.0-75ddd7b.js`): the Qt build of Plex Web replaces the web profile with its own. It sends `X-Plex-Client-Profile-Name: Plex Desktop`. It declares video direct play for the containers 3gpp, asf, avi, mkv, mov, mp4, mpeg, mpegts, rm and wtv over HTTP, HLS and DASH (DASH preferred), and audio direct play for aac, ac3, aiff, asf, dts, flac, mkv, mp3, mp4, ogg and wav. It never burns subtitles in for direct play, declares that the display can show HDR but not Dolby Vision, and turns direct play off for Live TV. The video player component reports its player type as `mpv`. The bundle knows four player kinds (`html`, `mpv`, `samsung_avplay`, `webmaf_video_player`).
- **observed** (`Profiles/Plex Desktop.xml` in the bundled server): the server-side `Plex Desktop` profile turns on stream selection during direct play. Its transcode targets are MKV over HTTP (video h264, hevc or any; audio opus, vorbis, flac or any; subtitles ass, pgs, vobsub or any), in both a `streaming` and a `static` context.

### When each falls back to server transcoding

- **observed**: both UIs ask the source server for a decision (`/video/:/transcode/universal/decision`, then `start`, plus a `ping` to keep the session alive) and send the profile above. They read back the server's decision codes (`mdeDecisionCode`, `transcodeDecisionText`). The server transcodes when the file is outside what the client declared, when the user picks a quality below original, when the user turns direct play off, or for Live TV on desktop. Otherwise the client direct plays or direct streams the file and mpv decodes it locally. Both clients have a transcode protocol (HTTP, with MKV as the target), so server transcoding is a fallback they keep, not one they lean on for ordinary files.
- **Not settled**: how often each client transcodes in practice, because no client ran against a server here. The Plex-specific `*_eae` decoders, and the bundled server's codec download path (`NanoServer::getCodecsDir`, `Player::onErrorDownloadingCodecs`, and strings such as "Codec %s is EAE and so it always needs downloading"), suggest some audio decoding depends on a codec Plex downloads at runtime. Which formats this covers is not settled.

### Verdicts on the playback claims

- ADR 0010, "Their own first-party apps also decode on the device (… Plex HTPC with mpv)": **confirmed**. HTPC declares nearly every codec, including VC-1, MPEG-2, VP9, AV1, TrueHD, DTS, PGS and VobSub, for direct play, and decodes them in libmpv with ffmpeg, using VideoToolbox where available. Plex desktop does the same.
- ADR 0010, "Server transcoding as the fallback every client leans on, as Plex, Jellyfin and Emby's web …": **contradicted for these two Plex clients**. Both keep server transcoding as a fallback, but the fallback is not their primary path, because they declare broad direct play. The sentence may still hold for Plex Web in a browser, which is not in this note's area.
- CC-11, "Plex uses server transcoding as the fallback": **confirmed** in the narrow sense: both clients fall back to a server transcode (MKV over HTTP) when direct play is ruled out.
- CC-11, "Plex HTPC with mpv": **confirmed**.

## Downloads

- **Plex desktop: supports Downloads on the Mac.** **observed**: the bundle has a Downloads library page ("{storageTotal} Downloaded", "You have no items downloaded"), Download settings for video and music quality, and show rules (`/media/subscriptions`, `…/process`, `…/template`). **observed**: the flow runs through the bundled server. When that server needs a download, the UI asks the source server for a decision with direct play and direct stream allowed, at the user's download quality (original by default), and passes the decision to the bundled server ("[Downloads] Sending decision to nano"). The bundled server then fetches the file (its `strings` include `/sync/%s/library/parts/%d/%s`). It is reached on a free local port it picks (`NanoServerManager::findFreePort`, disassembled), and it is given the account token and client identifier (`NanoServer::setAccessToken`, `setClientID`). It ships its own empty `com.plexapp.plugins.library.db`. **documented**: "Our desktop Plex apps for Windows, Mac, and Linux have the ability to download media from your Plex Media Server". Downloads need Plex Pass, the owner's permission and Plex Media Server 1.16.3 or newer, and they are stored in `~/Library/Application Support/Plex/Plex Media Server/Sync/` ([Downloads on Desktop](https://support.plex.tv/articles/downloads-on-desktop/), fetched 11 Oct 2026). The same page says playing a downloaded Item from the server's library streams it: only the Downloads library plays the Download.
- **Plex HTPC: no Downloads observed.** The UI has a `downloads` route identifier but no Downloads screen, no subscription endpoints and no bundled-server download handoff (`rg` through the HTPC web client). HTPC still starts the bundled server (same native classes), and from the bundles that server is seen only to supply codecs. **documented**: the HTPC release notes mention "Support for loopback servers and offline usage" (1.13.0) and switching Home users when plex.tv cannot be reached, but not Downloads ([release thread](https://forums.plex.tv/t/plex-htpc/703783)).

## How each talks to plex.tv and the server

- **observed**: sign-in and server discovery go through plex.tv. Both UIs use `/api/v2/pins` (PIN sign-in; HTPC shows `plex.tv/link`) and `/api/v2/resources` (the server list with its connections), and desktop also uses `/api/v2/users/signin`. Neither UI does local network discovery itself. GDM lives in the bundled server (its `strings` show `239.0.0.250`, `M-SEARCH * HTTP/1.1`, `GdmRequestHandler` and "Enable local network discovery (GDM)"). No GDM or port strings appear in either main executable.
- **observed** (connection choice): both score a server's connections. They prefer non-relay over relay (HTPC subtracts a point for relay), loopback over remote, local or private addresses, and HTTPS. Both recognise `*.plex.direct` hosts. HTPC builds a loopback connection `127-0-0-1.<hash>.plex.direct:32400` for a server on the same machine, and the HTPC status screen labels connections "Nearby", "Remote" and "Indirect" (relay).
- **observed** (headers): `X-Plex-Product` (desktop: taken from the native side, whose strings include "Plex for Mac"; HTPC: taken from the app config, and the native strings include "Plex HTPC"), `X-Plex-Version`, `X-Plex-Client-Identifier` (kept natively under `user-data/plex/client-id`), `X-Plex-Platform`, `X-Plex-Device-Name`, `X-Plex-Features` (`external-media,indirect-media`, and desktop adds `hub-style-list`), `X-Plex-Session-Identifier`, and the playback and session IDs.
- **observed** (token): API calls made with XHR or fetch carry `X-Plex-Token` as a **header** (desktop `getHeaders`, HTPC request headers). Every URL handed to something that cannot set headers carries it in the **query**: media and transcode URLs for mpv (`appendToken`), image and thumbnail URLs, subtitle URLs, websocket URLs and ad URLs. The native code has `?X-Plex-Token=%@` too.
- **observed** (live updates): both open a websocket to the server's `/:/websockets/notifications`, with the token in the query. HTPC also opens a websocket to `wss://pubsub.plex.tv/sub/websockets/<server id>/<client id>`, one per server, with the token in the query. What it carries was not traced. Watch Together rooms are a separate plex.tv service (`together.plex.tv/rooms`).
- **observed** (remote control): HTPC is a remote-controllable player through a server proxy. It registers with plex.tv (`PUT /devices/<client id>` with `X-Plex-Provides: client,player` and `proxiedBy` set to a chosen server), long-polls that server's `/player/proxy/poll` (`deviceClass=pc`, protocol version 2, with capabilities for timeline, playback, navigation, play queues and provider playback), and posts timelines to `/player/proxy/timeline`. No local listening port for remote control (such as 32500 or 32433) appears in either bundle. The desktop UI is a controller only: it sends `/player/playback/playMedia` and polls `/player/timeline/poll` on other players, and registering itself as a player is not observed.

### Verdicts on the API claims

- ADR 0012, "Plex documents passing `?X-Plex-Token=`": **confirmed as practice** in these clients, which put the token in the query of every media, image, subtitle and websocket URL. They use the header for ordinary API calls. Whether Plex *documents* it is not in this note's area.
- ADR 0013, "Plex shares one offset in milliseconds (`viewOffset`) across the versions of an item": **consistent on the client side, units unsettled**. HTPC reads the resume offset from the Item's `viewOffset` and picks the Version (`mediaIndex`) separately. Its timeline report (`/:/timeline`) names the Item (`ratingKey`, `key`) with `time` and `duration` and no Version identifier. Nothing in the client keeps an offset per Version. That the unit is milliseconds is not proven here: the client only treats `viewOffset` in the same unit as the Item's `duration`.
- ADR 0014, "Fetching per screen, as Plex and Jellyfin do": **confirmed** for these clients. Neither web UI keeps a local copy of the Library (no IndexedDB, Web SQL or service worker in either bundle). Both page through server responses with `X-Plex-Container-Start` and `X-Plex-Container-Size`, and screens load their own data as they open. The one local store is desktop's bundled server, which holds only Downloads.

## What could not be settled, and why

- How often each app transcodes in practice, and the server's exact decision for a given file, because no app was run against a server (browserless, no account).
- Whether Plex desktop ever plays video through Chromium's own `<video>` element instead of mpv (for example trailers, ads or Live TV). The bundle contains both player kinds. Only the mpv path was traced.
- Which audio formats need the runtime-downloaded EAE codec, and what HTPC's bundled server does beyond supplying codecs.
- The default of the hardware-decoding setting. The native side maps it to `auto` or `no`, but its first value comes from the UI's settings store and was not traced.
- The `static` transcode context in the `Plex Desktop` profile is probably the Download path, but no code tying the two together was found.
